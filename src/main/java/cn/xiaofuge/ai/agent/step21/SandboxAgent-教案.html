一、沙箱是什么：你天天都在用

沙箱（Sandbox）= 给不可信的代码划一块「可以活动的地方」，出了边界就被拦下。 它不是把危险代码「劝住」，而是把它关起来：在里面它爱怎么折腾怎么折腾，但碰不到外面的真实世界。

其实你每天都在享受沙箱的保护，只是没注意到：

  • 手机 App 沙盒：iOS / Android 上每个 App 只能读写自己的目录；相册、通讯录要弹窗授权，没授权就碰不到——这就是沙箱 + 权限系统；
  • 浏览器标签页：Chrome 把每个网页放在独立的「沙箱渲染进程」里，网页里的恶意代码就算执行了，也读不到你的文件系统；
  • Docker 容器：你跑过的容器就是一个文件系统视图被裁剪过的沙箱——容器里「看不见」宿主机的其他文件；
  • 微信小程序：小程序代码跑在受限的运行环境里，没有授权就调用不了摄像头、文件系统。

一句话记住它的本质：沙箱不是防它做坏事，而是「做了也做不成」——把最坏结果的伤害半径封死在边界之内。

二、Windows / macOS / Linux 分别怎么用沙箱

三家操作系统的实现机制不同，但思想一致：在内核（操作系统最底层）划边界，而不是靠程序「自觉」。

macOS —— Seatbelt（本课实验用的就是它）

macOS 内置 Seatbelt 机制：写一份 profile 文件声明「允许什么、拒绝什么」，再用系统自带的 sandbox-exec 命令包住你要跑的程序。Claude Code 在 macOS 上的沙箱正是构建在它之上的。

# profile 语义：默认放行，但禁写、禁网，只放行工作区写入，凭据目录禁读
(version 1)
(allow default)
(deny file-write*)
(allow file-write* (subpath "/Users/me/project/sandbox"))   ; 只有工作区可写
(deny network*)                                             ; 网络默认禁
(deny file-read* (subpath "/Users/me/.ssh"))                ; 凭据禁读

# 用它包住命令运行（本课 seatbelt-demo.sh 干的就是这件事）
sandbox-exec -f profile.sb /bin/sh -c "echo hi > sandbox/ok.txt"     # 放行
sandbox-exec -f profile.sb /bin/sh -c "echo hi > /tmp/evil.txt"      # 内核拒绝：Operation not permitted

另外，从 App Store 装的 Mac 应用都带 App Sandbox（声明式权限），和手机上 App 沙盒是同一思想。

Linux —— namespace + seccomp（容器技术的地基）

Linux 用三个「内核积木」搭沙箱，你熟悉的 Docker 就是它们的封装：

  • namespace：让进程「看见」一个被裁剪过的世界——mount namespace 里只挂载允许的目录，别的根本看不见；
  • seccomp：过滤系统能发起哪些系统调用——危险的调用直接被内核拒绝；
  • cgroups：限制 CPU / 内存用量，防止把机器拖垮。
# bubblewrap：轻量命令行沙箱（Claude Code 在 Linux 上用它）
bwrap --ro-bind / / --bind ./sandbox ./sandbox --unshare-net -- sh -c "命令"

# Docker：最常见的容器沙箱 —— 只挂载工作区、断网、只读根文件系统
docker run --rm -v "$PWD/sandbox:/ws" --network none alpine sh -c "cd /ws && 命令"

Windows —— AppContainer 与 Windows Sandbox

  • AppContainer：Windows 给 UWP 应用 / Edge 浏览器进程用的低权限容器——进程被打了「低完整性」标签，默认摸不到用户文档；
  • Windows Sandbox：Win10/11 专业版自带的一次性干净系统，用 .wsb 配置文件声明能访问宿主机的哪些目录，关掉即全部销毁——适合跑不信任的安装包；
  • Job Object：老牌机制，把一组进程捆在一起做资源限制（Chrome 在 Windows 上就用它做标签页沙箱）。
系统核心机制典型用法你在哪见过它
macOSSeatbelt（profile + sandbox-exec）、App Sandboxsandbox-exec -f xx.sb 命令App Store 应用、Claude Code
Linuxnamespace + seccomp + cgroups（bubblewrap / Docker）bwrap … 或 docker run …服务器容器、CI 流水线
WindowsAppContainer、Windows Sandbox、Job Object.wsb 文件双击启动一次性系统Edge/UWP、测试可疑软件
三家殊途同归：边界写在内核里，由操作系统强制执行——就算程序自己想越界、被恶意代码操控想越界，越界动作在系统调用这一层就会被拒绝。这就是和「写个 if 检查一下」的本质区别。

三、AI Agent 为什么特别需要沙箱

Agent 会替你执行 shell 命令，而模型是概率性的——它可能：

  • 犯错：幻觉出错误路径、理解错任务，把 rm 指向了不该删的地方；
  • 被诱导：读到网页/文件里藏的恶意指令（提示注入），真的去执行危险命令——注入骗得了模型，骗不了操作系统；
  • 泄密：把密钥文件读进上下文，随后发给外部 API。

Anthropic 官方的结论一句话：审查「它做了什么」是概率性的（连人工审批都被 93% 的批准疲劳打穿），约束「它能碰什么」才是确定性边界。所以 Claude Code 的做法是：默认禁写、只放行工作区、凭据目录禁读、网络代理白名单默认为空——然后把沙箱内的安全操作自动放行，只把沙箱兜不住的升级给人审。沙箱不只是安全设施，还是 Agent 跑得快的前提。

四、延展到本课：课程里怎么用沙箱

本课的 SandboxAgent 把上面的思想落成一个可以跑的教学版：模型通过 Function Calling 发起 shell_execute 工具调用，宿主用四层校验决定放行还是拦截，拦截结果回灌给模型让它自己修正。

1. 四层校验管线（应用层 = 策略：决定边界划多大）

图 1 · 与 step19/20 同构的单循环；唯一差别是工具结果来自「四层沙箱校验」
注意第 3 层的定位：黑名单是「不完备规则集」——rm -fr（参数换序）、 echo 编码 | base64 -d | sh（间接执行）都能绕过它。它只能防呆；防贼靠第 2 层的确定性边界，加上第 4 节的真沙箱。

2. 真沙箱执行：命令交给 macOS 内核看管

四层校验全过之后，命令不是在 Java 里直接跑，而是交给 macOS 自带的 Seatbelt 沙箱执行—— 这就是第一节讲的机制直接落到课程里：

// SandboxAgent.java · execute() 的核心逻辑（简化示意）
private String execute(String cmd) {
    String real = execInSeatbelt(cmd);      // ① 优先：放进真沙箱
    if (real != null) return real;
    return execSimulated(cmd);              // ② 回落：环境不支持时模拟（trace 会标注）
}

// execInSeatbelt()：生成 profile（第一节那份），命令由沙箱化的 /bin/sh 执行
new ProcessBuilder("sandbox-exec", "-f", profile, "/bin/sh", "-c", cmd)

两层分工要分清：四层检查是策略层（决定边界划多大），Seatbelt 是强制层（保证边界真的有效）。 就算模型用编码、变量间接引用等手段骗过全部字符串检查，越界写的系统调用照样被内核拒绝——命令「想做」和「能做」从此分离。

3. 拦截 → 修正 → 放行：完整时序

图 2 · 与 step20 时序同形状：都是「宿主裁决 → role=tool 回填 → 回到同一循环」；差别只在裁决依据（风险矩阵 vs 四层沙箱）

4. 与 step20 审批的组合关系

审批管「该不该做」（权力，事前人拍板），沙箱管「做的时候能碰什么」（能力，事中内核强制）——两层串联缺一不可。 官方原文："Sandboxed commands still go through the regular permission flow"（沙箱内的命令仍要走权限审批流）。

实验 B · Agent 在环（SandboxAgent.java，IDEA / Terminal）

六、常见问题

问题答案要点
既然有边界层，黑名单还要不要？要，但摆正位置：防呆 + 纵深之一，挡最常见的蠢命令；绝不能因为它存在就以为安全。
拦截了为什么不直接终止任务？协议要求每个 tool_call 必须有 tool_result；假成功会骗模型报喜、丢弃会破协议。verdict 如实回灌 → 模型可修正（实测它自己改成了 ls sandbox）。
沙箱和审批会不会重复打扰？串联组合：沙箱内的安全操作自动放行，出网/越界才升级审批——沙箱让审批「少而准」。
四层检查都在 JVM 里，那还是沙箱吗？四层是策略层（划边界），Seatbelt 才是强制层（守边界）。真实系统两者都要：策略 + 内核强制 = 完整沙箱。
沙箱失效了怎么办？官方默认 fail-open（平台不支持就裸跑），可配置 fail-closed。思考题：哪些场景必须 fail-closed？（生产库、金融、医疗）

七、课后练习

  1. 跑通实验 A / B：记录第 5 项测试的内核回执，用自己的话解释「为什么编码绕过对内核无效」；
  2. 跨系统：Windows 同学用 Windows Sandbox（.wsb）复现「只挂载工作区」；Linux 同学用 bwrap 或 Docker 复现实验 A 的五项测试；
  3. 补网络代理：给第 4 层实现 allowlist（默认空）+ 每域名首次审批，对齐官方 network.allowedDomains；
  4. 串联两节：给 shell_execute 加上 step20 审批门禁（高危先问人、批准后再过沙箱），画一张「审批 → 沙箱 → 执行」组合时序图；
  5. 读官方文档：code.claude.com/docs/en/sandboxing 与 anthropic.com/engineering/how-we-contain-claude，各提炼 3 条教学版没有的机制。

八、三句话带走

1. 沙箱不是防它做坏事，而是做了也做不成——伤害半径被封死在边界内。

2. 门禁管该不该做（step20 权力），沙箱管能碰什么（step21 能力）——黑名单防呆，边界防贼。

3. 拦截不是终点：verdict 回灌，模型自纠，人看全程——透明本身就是安全的一部分。
