先制造困境

如果让一个大脑干所有事，会发生什么？

做一个实验：让单个 Agent 一口气完成「调研 → 写作 → 审查」，并把它的完整上下文打印出来。随着轮次增加，你会亲眼看到——

注意力稀释
搜索日志、中间草稿、重试错误全堆在一个上下文里，模型越聊越糊涂，开始忘记最初的要求
角色打架
写手的发散提示词和审查员的挑剔提示词混在一条系统消息里，互相抵消，谁也调优不动
错误无人拦
既当运动员又当裁判，自查自查，一路错到底也没有独立反馈喊停
官方给这种现象起了个名字：Context Rot（上下文腐化）——主会话只应装需求与决策，不装噪声。 这不是模型不够强，而是「单大脑架构」的必然结局。
真实场景

真实产品已经给出了同一个答案

Codex、Claude Code、WorkBuddy 的多智能体设计高度一致，核心就三条。Step12 就是把这三条各对应一处代码。

产品级设计真实工具里的样子ToyAgent 里对应
角色是配置文件 Codex 用 .codex/agents/*.toml，Claude Code 用 .claude/agents/*.md 声明名字 + 职责 + 提示词 + 工具白名单 Map<String, AgentSpec> ROLES 注册表
上下文隔离 每个子代理在全新上下文里干活，搜索结果、草稿、日志留在内部，只回传「结论摘要」 dispatch() 每次新建消息列表
质量门禁 + 循环护栏 审查员是独立角色（Codex 的 reviewer 挂只读沙箱），不通过打回重做，但最多 N 轮（max_iterations） MAX_REVIEW_ROUNDS = 2 的审查循环

读者视角：摸清这三条，就摸到了所有主流 Agent 产品的多智能体骨架。

设计之一

角色是「数据」，不是「代码」

// 角色注册表 —— 等价于 .claude/agents/ 目录
private static final Map<String, AgentSpec> ROLES = new LinkedHashMap<>();
static {
    ROLES.put("planner", new AgentSpec("planner", "🧭", """
        你是规划者。把任务拆解为三个角色的执行计划…
        """));
    ROLES.put("researcher", new AgentSpec("researcher", "🔬", """
        你是研究员。围绕任务输出 3 条以内研究要点…
        """));
    // writer / reviewer 同理…
}
加一个角色

一行 put，流程零改动

协作流水线只认注册表的 key，不关心里面装了谁。想加一个「译者」「画师」？加一行配置，主流程一行代码都不用动。

这是开闭原则的 Agent 翻版

对扩展开放，对修改关闭

角色是数据（提示词、名字、emoji），不是硬编码的 if-else。这正是早期硬编码 Agent 与现代 Agent 框架的分水岭。

设计之二

上下文隔离 —— 团队感来自「每次从白纸开始」

/// 派遣一个角色 —— 多智能体的最小执行单元
private String dispatch(String key, String task) {
    AgentSpec spec = ROLES.get(key);
    return model.chat(
        List.of(                        // ← 全新消息列表
            Message.system(spec.system()),
            Message.user(task)
        )
    ).trim();
}

所谓「一支团队」，只是每次调用都从空上下文开始。

过程噪声，留在子代理内部

研究员翻了几千 token 的资料

搜索日志、读了一半的文档、试错记录——全部随子代理的上下文一起「用完即焚」。主线只收到 3 条要点摘要。

写手只拿摘要

而不是研究员的完整过程

dispatch("writer", "任务 + 研究笔记") —— 主线始终保持干净：只装需求、决策与结论。这就是对抗 Context Rot 的第一现场。

设计之三

质量门禁 + 循环护栏 —— 有反馈，但不许失控

sequenceDiagram participant W as ✍️ 写手 participant V as 🔍 审查员（独立上下文） W->>V: 提交草稿 V-->>W: ❌ {"pass": false, "comment": "一句话点评"} Note over W: 带审查意见重写（全新上下文） W->>V: 提交修订稿 V-->>H: ✅ {"pass": true} participant H as 🏁 主持者 Note over V,H: 护栏 MAX_REVIEW_ROUNDS = 2
到轮次上限即使未过审也带意见交付
审查员与写手互不共享上下文——独立视角才有真判断力；护栏防止二者无限打转。
为什么要独立角色审查

写手自查自己，等于既当运动员又当裁判。审查员在全新上下文里只看稿子本身，没有被写作过程「带节奏」，才能给出真评价。

为什么必须设护栏

有反馈回路但没有护栏的系统是失控系统。真实工具的 max_iterations / kill criteria 与这里的 MAX_REVIEW_ROUNDS = 2 是同一件事。

这类思想来自哪里

两百年的分工智慧，四十年的学术积累

timeline title 多智能体思想源流 1776 : 组织学起点 —— 亚当·斯密《国富论》：分工让专责角色完成大任务（康威定律是其工程投影） 1986 : 认知理论 —— Minsky《Society of Mind》：智能是大量简单 agent 相互作用的涌现 1980s : 学术起点 —— 分布式 AI / 黑板系统：Hearsay-II 用多个「知识源专家」在共享黑板上协作 2023 : LLM 时代点火 —— AutoGPT / BabyAGI 引爆；CAMEL、MetaGPT、AutoGen 成型「角色扮演软件公司」范式 2024 : 极简收敛 —— OpenAI Swarm / Agents SDK 把多智能体收敛成最小原语 2025 : 产品化 —— Claude Code / Codex subagents：角色即配置文件，成为所有主流产品的标配
多智能体不是新发明，而是把几百年验证过的组织学方法，搬进了 prompt。
价值总结

三座大山，三个动作

单个 LLM 干复杂任务的三座大山，被「分工 + 隔离 + 审查闭环」三个动作同时拆掉。

单大脑的困境多智能体的动作价值
上下文被过程噪声腐化 子代理独立上下文，只回传摘要 主线只装需求与决策，长任务不「越干越糊涂」
角色混杂，提示词互相打架 角色即数据：注册表一行一个角色 每个角色可单独调优、按任务选模型、加角色不改流程
无独立反馈，一路错到底 独立审查员 + 打回循环 + 轮次护栏 质量闭环可控收敛，既当裁判又不许失控
这就是它从学术玩具变成所有主流产品标配的原因
记住一句话
多智能体最反直觉的地方在于：
团队感不是来自多个模型，
而是来自每次对话都从一张白纸开始。 读者记住这句话，就记住了 dispatch() 那三行代码的全部意义。
